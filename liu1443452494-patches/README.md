# Amane 自用补丁与手动构建

补丁仅在 GitHub 构建工作区应用。仓库中的上游业务源码保持原样，定时同步继续使用现有的合并流程。软件内部版本沿用上游；手动输入的版本号只用于构建记录和发布产物。

## 补丁内容

按以下顺序检查并应用，顺序由 `build.py::prepare` 固定。缺少补丁、出现未登记的补丁或任一补丁应用失败，都会停止构建。禁止跳过失败补丁或自动解决冲突。

| 文件 | 修改内容 |
|---|---|
| `0001-library-images.patch` | 媒体库分别选择封面（thumb）、海报（poster）、缩略图（fanart）。fanart 复用资源目录中的封面原图；备用海报裁切直接读取原图，不依赖输出的 thumb。关闭 thumb 时不复制、覆盖或叠加其水印。不删除历史图片，不转换旧媒体库选择。 |
| `0002-nfo.patch` | 仅在 NFO 中省略导演，追加当前文件的中文字幕及有码／无码／破解标签；去重并保留顺序，连续输出全部 tag 后再输出同序 genre。原有 actor 节点、XML 转义和非法字符清理保留。演员标签的保存位置由 `0005-metadata-tags.patch` 统一到数据库。 |
| `0003-actresses.patch` | 仅修改路径模板的 `{actresses}`。沿用原有性别筛选，0 人保留 `Unknown`，1～3 人保留姓名，超过 3 人输出“多人作品”。不缩减数据库或 NFO 中的演员名单。 |
| `0004-actor-mapping.patch` | 每次取得影片刮削结果后、写入数据库前，按用户 XML 统一演员姓名。唯一匹配转换为标准名，歧义或未匹配保留原始输入并继续 Amane 原有流程。 |
| `0005-metadata-tags.patch` | 刮削保存时，将原始标签本地转为简体，再追加已完成姓名归一的完整演员名单，去重保序后写入数据库并同步标签关联。前端显示、标签筛选及 NFO 共用数据库标签；NFO 不再单独追加演员姓名。 |
| `0006-actor-delete.patch` | 删除演员时清理演员资料、别名及影片关联，不再自动生成剔除规则；后续影片刮削可按 XML 标准名重新创建演员。同步调整演员列表、详情页的删除提示及智能体说明。已有剔除规则继续保留。 |
| `0007-image-quality.patch` | 封面与海报遍历有效候选，按实际文件大小择优；内置 Tenhow、ASIN 日亚及日文标题回退检索，保护下载海报不被较低尺寸的裁剪结果覆盖。不增加前端开关或依赖。 |
| `0008-processing-log.patch` | 影片详情页按番号分别显示最近一次刮削和整理记录，突出处理文件路径；读取本地任务日志生成中文说明，并补充 ASIN、原始检索信息、图片尺寸、文件大小及选择原因。 |

NFO 的字幕标签沿用文件名和外挂字幕识别结果，不检查字幕实际语言；马赛克性质优先使用文件标记，再参考影片类型。破解不会额外自动追加有码或普通无码。自动生成的文件标记只用于当前文件的 NFO，不写入同一番号共用的数据库标签；刮削来源原本提供的同名标签继续保留。

标签繁转简复用项目已有的 `zhconv`，使用保留原有用词的通用简体模式，不增加依赖、不联网，也不需要启用或配置 LLM。只转换原始标签，演员姓名保留 XML 映射及原有别名处理后的结果。刮削保存仍尊重标签锁定及现有分类规则，不修改来源原始快照；手动编辑标签不触发自动转换或追加。

已存在的影片需要重新刮削、保存后才会获得数据库标签；允许复用原始刮削缓存，不必强制重新获取站点数据。已锁定的标签保持原值。磁盘上已有的 NFO 在下一次整理写入时更新，不进行自动批量回填。

自定义水印使用原有数据目录的 `watermarks/` 功能。补丁不引入 CDATA、Jinja2，也不修改 `{number}` 的大小写规则。

## 演员姓名映射

固定读取当前数据目录根目录的 `mapping_actor.xml`，与 `config.toml`、`amane.db` 同级。

- Windows：通过软件菜单“打开数据目录”，将 XML 复制到该目录根目录。
- Docker：默认容器路径为 `/data/mapping_actor.xml`，在宿主机对应的数据挂载目录中维护文件。
- XML 由用户提供，不会自动下载、覆盖或随镜像内置。文件使用 UTF-8，支持 UTF-8 BOM。
- 每条 `a` 记录的 `zh_cn`、`zh_tw`、`jp` 与逗号分隔的 `keyword` 均参与完整姓名匹配，清除姓名两端的空白。
- 唯一匹配后使用该记录的非空 `zh_cn`。多个记录指向相同标准名不算歧义；同名对应不同标准名时跳过该姓名的映射。
- 每次刮削重新读取文件，修改后对下一次取得刮削结果的任务生效；缺少文件时继续原有流程。文件格式或编码损坏时，当前任务会报告明确的读取错误。
- 原始姓名交给项目已有的别名机制保留，供演员资料查询使用；性别、名单顺序和来源原始快照保留。
- 后续展示名修改和演员合并继续采用原有机制，不强制覆盖数据库展示名，也不迁移已整理的目录。

## 演员删除

需要按更新后的 XML 重新创建演员时，先维护 XML，再删除对应旧演员，随后重新刮削相关影片。影片的演员字段需要未锁定；通过扫描批量处理时，刮削范围需要包含“已刮削”。允许复用元数据缓存，XML 映射仍会重新执行，不需要重启。

数据库中已经保存的演员剔除规则不会自动清除。需要恢复对应演员时，在“演员 → 列表视图 → 分类规则”中移除其姓名及相关别名的剔除规则，再重新刮削。移除规则不会恢复旧演员资料；其他影片中被移除的演员关联需要各自重新刮削，文件夹和 NFO 需要重新整理。

## 高清图片

封面（thumb）与海报（poster）按实际文件字节数选择，不以像素数量或响应头中的大小代替。全部候选均参与检查；有效缓存可以复用，损坏图片和返回 HTML 的地址不参与排序。普通来源同大小时沿用字段优先级和站内顺序；海报同大小优先日亚，Tenhow 排在普通来源之后。

海报检索流程固定内置：

1. 收集普通刮削来源的海报候选。
2. 使用 DMM 原始日文演员名，在 Tenhow 目录及必要的五十音子目录定位演员。核对同一作品区块中的 DMM 商品编号后，取得图片链接和 ASIN；图片下载失败不影响已核实 ASIN 的后续使用。
3. 使用 ASIN 访问日亚商品页，仅提取通过身份核对的商品主图，同时尝试主图原始地址和页面提供的缩放地址。
4. 未取得有效日亚图片时，使用 DMM 原始日文标题搜索 DVD，并结合演员信息核对作品。标题路径核实的新 ASIN，在日亚图片仍失败时继续尝试 Tenhow 图片直链。
5. 已取得的普通来源、Tenhow 和日亚图片共同按文件大小比较。ASIN 路径取得有效日亚图片后跳过标题搜索，即使该图片比已有海报更小。

搜索不使用翻译后的标题或 XML 映射后的标准演员名。DMM 缺少信息时，仅使用其他来源明确提供的日文快照或包含日文假名的原始信息。相同商品页和图片地址在一次处理内去重，同一 ASIN 的新图片地址仍可参与比较。网络失败只影响当前检索，不永久判定 ASIN 无效。

裁剪继续遵守原开关、比例与触发条件，使用选定封面作为原图。裁剪结果宽、高均不小于下载海报且至少一项增大时才替换；同尺寸、较小、宽高各有优劣或裁剪失败时保留下载海报。裁剪结果按尺寸比较，不按重新编码后的文件大小比较。

新图全部失败时保留旧图；首次刮削没有旧图时继续原有缺图处理。原有下载设置、字段锁定和媒体库复制设置继续生效。fanart 继续复用封面原图，超分由上游维护；使用本补丁时按既定方案关闭超分。站点覆盖范围、页面变动及访问限制可能导致高清来源无结果，此时保留已取得的普通来源图片。

## 处理日志

片库详情提供“处理日志”，按番号分别读取最近一次刮削和整理，包含进行中及失败任务；两类并存时通过标签切换，默认刮削，单类直接展示。宽弹窗固定标题、标签和刷新按钮，任务信息、完整路径及日志共用滚动区；短字段并排，长内容完整换行，不省略或折叠。顶部突出最近文件及存在的目标路径。同一番号的多个文件共用记录，明细保留各自路径；批量整理只显示当前番号，时间依据实际处理记录，任务状态与文件结果分别显示。

中文说明读取本机 `logs/tasks/` 内的任务过程日志及已有来源结果，由固定规则生成，不调用 AI 服务。图片明细记录原始演员名和标题、具体 ASIN、完整地址、候选尺寸、准确字节数、选中及裁剪原因；地址中的凭据会脱敏。新补丁增加记录信息，图片检索、文件大小排序与裁剪保护规则沿用 `0007-image-quality.patch`。弹窗打开时查询，活跃任务定时刷新，关闭后停止刷新。

旧任务中没有记录的路径、图片尺寸或文件大小明确提示缺失，不读取当前文件倒推历史。旧整理日志无法确认番号归属时不关联；任务删除或日志清除后不保留独立副本。日志缺失、损坏或过长时显示读取限制，不使用同批次其他影片的数据补充。

## GitHub 配置

在当前 fork 仓库的“Settings → Secrets and variables → Actions”中添加两个仓库密钥：

| 密钥 | 内容 |
|---|---|
| `DOCKERHUB_USERNAME` | Docker Hub 用户名 |
| `DOCKERHUB_TOKEN` | Docker Hub 个人访问令牌，需要镜像读取、写入权限 |

Docker 镜像固定发布到该账号下的 `amane`，仅构建 `linux/amd64`。上述密钥与已有的 `AMANE_SYNC_TOKEN` 相互独立，不需要修改上游同步密钥。

Windows 发布使用 Actions 自带的 `GITHUB_TOKEN`，工作流已声明 `contents: write`，无需额外提供 GitHub 个人令牌。若仓库或组织策略禁止写入，发布会失败，需要在 GitHub 设置中允许工作流写入仓库内容。

## 手动构建

将自用文件提交并推送到 fork 的默认分支后，在 GitHub Actions 中选择：

- “自用 Windows 压缩包”：产出 x64 ZIP，保存 Actions 下载产物，并发布到该版本的 GitHub Release。
- “自用 Docker 镜像”：构建 amd64 镜像，推送到 Docker Hub。

点击“Run workflow”，选择包含补丁的分支并填写版本号，再手动运行。两个工作流都没有 push、tag 或定时构建触发器。

版本号以小写 `v` 和数字开头，建议使用 `v1.0.0` 这样的格式。允许数字版本以及 `-alpha.1` 一类后缀，不允许空格、路径字符或超过 128 个字符。编号由用户递增，不自动修改源码版本。

| 项目 | 输入 `v1.0.0` 时的结果 |
|---|---|
| Windows 构建记录 | `Windows 压缩包构建 · v1.0.0` |
| Docker 构建记录 | `Docker 镜像构建 · v1.0.0` |
| Windows 文件 | `Amane-v1.0.0-windows-x64.zip` |
| GitHub Release 标签 | `v1.0.0` |
| Docker 标签 | `1.0.0` 和 `latest` |

同一版本的 Windows 和 Docker 可以分别运行。Windows 检查到同名 Git 标签或 Release 已存在时会停止，避免将新构建关联到旧源码；需要重新发布时填写新版本。Docker 同一版本重跑会更新该镜像标签及 `latest`。

应用补丁后执行 Python 格式与类型检查，以及图片、NFO、演员目录命名、姓名映射、数据库标签、演员删除和处理日志的逻辑测试；覆盖高清检索与回退、文件大小排序、裁剪保护、删除后按 XML 重建、字段锁定、番号隔离、历史路径、日志缺失及异常输入。前端 OpenAPI 和客户端类型在构建时通过根目录 `Justfile` 重新生成，不保存在补丁中。Windows 沿用 `just windows-app`；Docker 沿用上游 `Dockerfile`。

## 同步与失败检查

自用文件集中在 `liu1443452494-patches/`，两个工作流使用 `.github/workflows/liu1443452494-build-*.yml`。这些路径用于降低与上游重名的概率；合并式同步会保留 fork 独有文件，同路径变更仍可能产生合并冲突。

构建失败时，先查看失败步骤及 Actions 摘要。摘要记录构建编号、源码提交和已应用的补丁；应用错误包含补丁名称及 Git 报告的相关文件。部分补丁已成功应用后发生失败，也不会继续编译或发布，修改只留在该次构建工作区。

检查上游相关源码后，仅更新受影响的补丁，再执行验证并使用新版本号手动构建。补丁成功应用不能证明语义兼容，逻辑测试仍是发布前的必要检查。
