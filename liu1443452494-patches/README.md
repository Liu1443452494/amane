# Amane 自用补丁与手动构建

补丁仅在 GitHub 构建工作区应用。仓库中的上游业务源码保持原样，定时同步继续使用现有的合并流程。软件内部版本沿用上游；手动输入的版本号只用于构建记录和发布产物。

## 补丁内容

按以下顺序检查并应用，顺序由 `build.py::prepare` 固定。缺少补丁、出现未登记的补丁或任一补丁应用失败，都会停止构建。禁止跳过失败补丁或自动解决冲突。

| 文件 | 修改内容 |
|---|---|
| `0001-library-images.patch` | 媒体库分别选择封面（thumb）、海报（poster）、缩略图（fanart）。fanart 复用资源目录中的封面原图；备用海报裁切直接读取原图，不依赖输出的 thumb。关闭 thumb 时不复制、覆盖或叠加其水印。不删除历史图片，不转换旧媒体库选择。 |
| `0002-nfo.patch` | 仅在 NFO 中省略导演。保留原标签，追加完整演员姓名、中文字幕及有码／无码／破解标签；去重并保留顺序，连续输出全部 tag 后再输出同序 genre。原有 actor 节点、XML 转义和非法字符清理保留。 |
| `0003-actresses.patch` | 仅修改路径模板的 `{actresses}`。沿用原有性别筛选，0 人保留 `Unknown`，1～3 人保留姓名，超过 3 人输出“多人作品”。不缩减数据库或 NFO 中的演员名单。 |
| `0004-actor-mapping.patch` | 每次取得影片刮削结果后、写入数据库前，按用户 XML 统一演员姓名。唯一匹配转换为标准名，歧义或未匹配保留原始输入并继续 Amane 原有流程。 |

NFO 的字幕标签沿用文件名和外挂字幕识别结果，不检查字幕实际语言；马赛克性质优先使用文件标记，再参考影片类型。破解不会额外自动追加有码或普通无码。原有标签中的内容保持不变。

自定义水印使用原有数据目录的 `watermarks/` 功能。补丁不引入 CDATA、Jinja2，也不修改 `{number}` 的大小写规则。

## 演员姓名映射

固定读取当前数据目录根目录的 `mapping_actor.xml`，与 `config.toml`、`amane.db` 同级。

- Windows：通过软件菜单“打开数据目录”，将 XML 复制到该目录根目录。
- Docker：默认容器路径为 `/data/mapping_actor.xml`，在宿主机对应的数据挂载目录中维护文件。
- XML 由用户提供，不会自动下载、覆盖或随镜像内置。文件使用 UTF-8，支持 UTF-8 BOM。
- 每条 `a` 记录的 `zh_cn`、`zh_tw`、`jp` 与逗号分隔的 `keyword` 均参与完整姓名匹配，清除姓名两端的空白。
- 唯一匹配后使用该记录的非空 `zh_cn`。多个记录指向相同标准名不算歧义；同名对应不同标准名时跳过该姓名的映射。
- 每次刮削重新读取文件，修改后对下一次取得刮削结果的任务生效；缺少文件时继续原有流程。文件格式或编码损坏时，当前任务会报告明确的读取错误。
- 原始姓名交给项目已有的别名机制保留，供演员资料查询使用；性别、名单顺序和来源原始快照保留。
- 后续展示名修改和演员合并继续采用原有机制，不强制覆盖数据库展示名，也不迁移已整理的目录。

## GitHub 配置

在当前 fork 仓库的“Settings → Secrets and variables → Actions”中添加两个仓库密钥：

| 密钥 | 内容 |
|---|---|
| `DOCKERHUB_USERNAME` | Docker Hub 用户名 |
| `DOCKERHUB_TOKEN` | Docker Hub 个人访问令牌，需要镜像读取、写入权限 |

Docker 镜像固定发布到该账号下的 `amane`，仅构建 `linux/amd64`。上述密钥与已有的 `AMANE_SYNC_TOKEN` 相互独立，不需要修改上游同步密钥。

Windows 发布使用 Actions 自带的 `GITHUB_TOKEN`，工作流已声明 `contents: write`，无需额外提供 GitHub 个人令牌。若仓库或组织策略禁止写入，发布会失败，需要在 GitHub 设置中允许工作流写入仓库内容。

## 手动构建

将自用文件提交并推送到 fork 的默认分支后，在 GitHub Actions 中选择：

- “自用 Windows 压缩包”：产出 x64 ZIP，保存 Actions 下载产物，并发布到该版本的 GitHub Release。
- “自用 Docker 镜像”：构建 amd64 镜像，推送到 Docker Hub。

点击“Run workflow”，选择包含补丁的分支并填写版本号，再手动运行。两个工作流都没有 push、tag 或定时构建触发器。

版本号以小写 `v` 和数字开头，建议使用 `v1.0.0` 这样的格式。允许数字版本以及 `-alpha.1` 一类后缀，不允许空格、路径字符或超过 128 个字符。编号由用户递增，不自动修改源码版本。

| 项目 | 输入 `v1.0.0` 时的结果 |
|---|---|
| Windows 构建记录 | `Windows 压缩包构建 · v1.0.0` |
| Docker 构建记录 | `Docker 镜像构建 · v1.0.0` |
| Windows 文件 | `Amane-v1.0.0-windows-x64.zip` |
| GitHub Release 标签 | `v1.0.0` |
| Docker 标签 | `1.0.0` 和 `latest` |

同一版本的 Windows 和 Docker 可以分别运行。Windows 检查到同名 Git 标签或 Release 已存在时会停止，避免将新构建关联到旧源码；需要重新发布时填写新版本。Docker 同一版本重跑会更新该镜像标签及 `latest`。

应用补丁后执行 Python 格式与类型检查，以及图片、NFO、演员目录命名和姓名映射的逻辑测试。前端 OpenAPI 和客户端类型在构建时通过根目录 `Justfile` 重新生成，不保存在补丁中。Windows 沿用 `just windows-app`；Docker 沿用上游 `Dockerfile`。

## 同步与失败检查

自用文件集中在 `liu1443452494-patches/`，两个工作流使用 `.github/workflows/liu1443452494-build-*.yml`。这些路径用于降低与上游重名的概率；合并式同步会保留 fork 独有文件，同路径变更仍可能产生合并冲突。

构建失败时，先查看失败步骤及 Actions 摘要。摘要记录构建编号、源码提交和已应用的补丁；应用错误包含补丁名称及 Git 报告的相关文件。部分补丁已成功应用后发生失败，也不会继续编译或发布，修改只留在该次构建工作区。

检查上游相关源码后，仅更新受影响的补丁，再执行验证并使用新版本号手动构建。补丁成功应用不能证明语义兼容，逻辑测试仍是发布前的必要检查。
